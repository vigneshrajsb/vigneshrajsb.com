Ditto

Draft · 9 min read

AI agents are great at the task you hand them. But most of my day isn't one task. It's the work around the work: who asked for what, which thread needs an answer, what I promised, what's waiting on someone else. It lives across Slack, email, tickets and my head, and some of it slips.

That's the part I actually want to hand off. It needs an agent that knows me, that I trust to act, and that isn't tied to whichever tool I'm using this month. Today, most agent sessions start from zero, and every new tool means setting everything up again.

My teammate Vahan built that agent. It's called Ditto, a personal agent for work. It reads the places your work happens, keeps one list you can trust, remembers your people and projects, writes in your voice, and learns from every correction. It isn't tied to one tool: the same setup runs in Claude Code and in Codex today, and it's built so the next harness can pick it up too.

I've been adopting it piece by piece. This post is how it's put together, and how you'd set up something like it for yourself with whatever harness you use.

Why “Ditto”

Ditto is the Pokémon that turns into a copy of whatever it looks at. This one starts knowing nothing about you and slowly becomes a copy of how you work: how you write, what you'd do first, who matters for what, and what you'd never put in a ticket.

Under the name, a personal agent needs five things. A home it always starts from. A way to run in any harness. Hands for the work. Context about you. And a loop that turns your corrections into trust. The rest of the post takes them in order.

1. Give it a home

Matt Pocock calls this the home repo pattern. Keep your skills, steering files and tooling in one repo, and point your agent at everything else from there.

Why I'm writing this

Until I saw Matt's short, I didn't think any of this was worth sharing. It felt like personal plumbing. Then it clicked: this setup is how you get to trust an agent, and trust is what lets you hand it more. Scaling with agents next depends less on bigger models and more on agents that know you and have earned the right to act for you.

Ditto is that pattern for a whole person, not just a codebase. Your Ditto is a folder on your machine (call it ~/Ditto), and you always open your agent there. Inside it are three layers.

  • Core is the engine: skills, rules, scripts, module manifests and templates. It never holds anyone's data. Vahan maintains it.
  • Packs hold what a team or company shares: its ticket site, chat workspace, approval rules and runbooks. They're optional, and they keep shared knowledge out of every person's home.
  • You is your layer: your profile, memory, writing voice, your own rules and logs. It's tracked in its own local git, with no remote.

This split is what made adopting it painless. I didn't fork Vahan's agent. I took his core, and every change I wanted went into my own layer as an override. When he ships an update, I pull it and my changes stay where they are.

2. Make the harness a thin shell

The harness is whatever runs the model loop: Claude Code, Codex, or whatever comes next. Ditto treats it as a thin shell. Each harness only needs an entry file it already knows how to read, and every entry file points at the same rules in the home.

Claude Code reads CLAUDE.md, which imports the core rules and your own. Codex reads AGENTS.md, which lists the same files. Skills get linked into each harness's skills folder by one install command, with a flag for the harness you use.

Models are handled the same way. The rules never name a model for a job. They name a tier, and each harness maps tiers to its own models:

TierUsed forIn Claude CodeIn Codex
TopArchitecture, deep research, long unattended runsThe largest modelIts most capable model, at higher effort
StrongThe default: planning, debugging, anything that mattersThe main modelIts most capable model
StandardWell-scoped work against a clear specThe mid-size modelIts default model
LightLookups, classifying, collecting raw itemsThe small modelIts smallest model

One rule sits on top: a cheaper model's output only counts after the strong model has checked it. When a new harness or model comes along, you update the mapping, and the rules stay as they are.

3. Give it hands, one module at a time

Ditto's features are modules, and you switch them on in your profile:

  • Task sync pulls asks from chat, email, tickets and saved messages into one task list.
  • Daily brief sums up your morning, with a link on every fact.
  • Meetings preps your 1:1s and takes notes.
  • Memory keeps track of people, projects and decisions.
  • Writing style drafts in your voice.
  • Code work picks up tickets in your repos.
  • Hub is a small menu bar app for everything that's waiting on you.

Each module ships a short manifest that says what it needs. Here's a simplified version of the format:

---
name: task-sync
summary: One task list from chat, email and tickets
connectors: [Slack, Gmail]
connectors_optional: [Jira]
profile: [task_store]
scheduled: [morning-sync]
---

A doctor script reads every manifest and checks your machine against it: connectors, command-line tools, sign-ins, permissions and files. Setup uses the same manifests, so it only asks about the modules you turn on. Adding your own module means adding another manifest, in your layer.

If you only turn on one module, make it task sync. Asks get scattered across five tools and a few always slip through. Having them in one list every morning, with the people waiting on you at the top, was the first thing that made Ditto feel worth it.

4. Teach it who you are

Ditto keeps three kinds of context, in plain files you can read and edit:

  • Memory covers people, projects, team-specific words, the services you own, and what other people decided that affects you, each with a link to where it was said. A weekly cleanup job tidies it, the way you'd go through your notes.
  • Voice is worked out from messages you've actually sent, so drafts sound like you and not like an assistant.
  • A self model describes how you decide, what you do yourself and what you delegate, and what you never do. Whenever Ditto has to make a call, it asks what you would do. It starts empty and only changes when you approve a proposed edit.

None of this is a database or a vector store. It's Markdown in a folder you own, so any harness can read it and you can always see why the agent did what it did.

5. Turn every correction into a rule

This is the part I'd copy first. Every message you send to Ditto is checked for a correction, a preference or a new fact: “too long,” “ask Pat, not the whole channel,” “never put that in a ticket.” Each one is filed in the same turn, in the most specific place that will be loaded when it matters. That could be a project's memory, a person's file, an override on one skill, or your general rules. Then Ditto tells you in one line what it kept and where.

You never have to say “remember this.” And when a correction contradicts an existing rule, Ditto doesn't quietly pick one. It asks whether this is an exception, a new general rule, or a one-off.

Once a week it reviews itself: what you corrected, what you ignored and what you redid. It proposes changes to its rules and your self model, and you approve them or not. Corrections that would help everyone go on a “propose to core” list for Vahan instead of staying in one person's home.

Ditto fixes its own tools, too. When a step fails, it reads the actual error, names the cause, fixes the script or skill, and re-runs only that step. Every run ends with a short report: what it did, what it healed, and what it skipped because only you could do it.

6. Let it earn the right to act

The point of all this isn't drafts. It's an agent that does the work: sends the Slack reply, files the ticket, opens the PR, nudges someone who went quiet. The question is how it gets there without you handing over the keys on day one.

Ditto keeps a ledger of everything it hands you, by kind of action, and whether you accepted it as is, edited it, or rejected it. Once a kind has ten or more answers, at least 90% accepted as is, and no rejection in the last ten, the weekly review proposes a standing OK for that kind, and only that kind. You grant it in your profile, and Ditto stops asking.

The guardrails sit next to that. Every kind of work session has an explicit list of tools it may use, and a list it may never use, however the request is worded. Your own rules can tighten the core safety rules but never loosen them. Memory and messages are never treated as instructions.

It's how trust works with a new teammate. Nobody gets every key in week one. They earn them one kind of task at a time, by getting it right the same way enough times in a row.

If you want to build your own

You don't need Ditto to get most of the value. Here's the smallest version I'd start with, in any harness:

~/agent/                 your home, git init, no remote
  CLAUDE.md              entry file for Claude Code, imports the rest
  AGENTS.md              entry file for Codex, lists the same files
  rules.md               how you want it to work
  profile.md             who you are, your tools, what it may do alone
  memory/                people, projects, words, one file each
  learning/feedback.md   every correction, dated, with where it went
  skills/                anything you've done twice
  1. Make the folder and always start there. Point the agent at your repos and tools from the home, not the other way around.
  2. Write one entry file per harness, and keep the real instructions in shared files they both load.
  3. Connect your tools read only. Let it read chat, email and tickets before you let it write anywhere.
  4. Add the learning rule on day one: “Every correction becomes a rule in the right file, and you tell me where.” That one line does more than any prompt you'll write.
  5. Schedule one morning run that turns yesterday's asks into a list.
  6. Keep a tally of what you accept as is. When a kind of action stops needing edits, let it do that on its own.

What I'm learning from Vahan

The thing that surprised me most is how little of Ditto is about the model. Most of it is plain files, with clear rules for where each piece goes. That's why it survives a model change, a new harness, and a new person adopting it.

A few weeks in, the drafts sound more like me, the morning list catches things I'd have dropped, and I correct the same thing at most once. It's not done, and that's by design: it gets better each week I use it.

Thanks, Vahan, for building it and letting me borrow it.
